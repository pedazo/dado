# OpenCode integration and installation

The adapter follows official OpenCode V2 documentation checked against installed `opencode v2.2.2` and the current official docs (agents, permissions, models, commands, skills, CLI). Project agents use `.opencode/agents/<name>.md`; primary/subagent modes are native; V2 permissions are `permissions` arrays of action/resource/effect rules. `/dado` and `/dado-profile` are native Markdown commands and the protocol is a progressive-disclosure skill. Named model profiles and their active name live in `.dado/config.yaml`; the active profile is rendered into DADO agent frontmatter as OpenCode's effective per-agent model configuration.

Without `--profile`, `dado models` always creates/edits `default`, regardless of which profile is active. `dado models --profile NAME` creates/edits the named profile; new profiles start as a copy of `default`. Editing an inactive profile only changes `.dado/config.yaml`, never active agent files. Bulk selection remains available for automation, e.g. `dado models --profile economical --model provider/model --variant high --roles dado-worker dado-explorer`; this path uses the existing `opencode models` CLI catalog and accepts the supplied variant ID.

Interactive `dado models` first displays every DADO role's current model and reasoning variant in the target profile, then accepts comma-separated role numbers or `all`, a provider, one of that provider's enabled models, and one of the model's advertised reasoning-variant IDs or the model default. The role selection applies one chosen model/variant to every selected role. A complete summary is shown before the final confirmation. Entering `0`, `q` or `quit` at a selection prompt, or declining the final confirmation, leaves configuration and agent files untouched. New profile creation and legacy profile initialization are also deferred until that final confirmation. Supplying `--model` or `--variant` (optionally with `--roles`) retains the noninteractive automation path; `--roles` alone scopes which roles are prompted.

The interactive catalog is retrieved with `opencode api get /api/model?location[directory]=…` for the resolved project directory. DADO validates the returned location, filters disabled models, and uses only the structured `variants[].id` values returned by OpenCode; it does not guess variant levels. Discovery has a bounded timeout and reports a clear error if the API or catalog is unavailable. The current V2 API documents `/api/model` as a location-scoped list-models endpoint: https://opencode.ai/v2/docs/api . `dado profiles list` shows the active and available profiles; `dado profiles use NAME` validates and applies every role's model/variant to all installed DADO agents, removing model frontmatter for inherited roles so no stale values remain. OpenCode's default model remains managed by OpenCode itself.

Run `/dado-profile NAME` in OpenCode to use the same `dado profiles use` path; without a name, the command lists active/available profiles and asks which to use. The profile applies to later agent invocations, not the current in-flight model. OpenCode normally reloads changed agent files automatically; if the new selection is not reflected, run `/reload` (no restart is required).

## Safe init and update

`dado init` creates missing `.dado` directories, config and project memory and installs only the DADO agent, command and skill files under existing `.opencode/`. The first migration imports existing role model/variant frontmatter into `default`; fresh installs use inherit. Later init/update calls preserve profile data and reapply the active profile to DADO-managed agent files, including after `--force` replaces templates. Pre-existing same-name files are treated as user-owned and preserved. DADO-installed templates get hashes in `.dado/managed-files.json`; on update, unchanged managed files may be refreshed, while locally modified files are preserved and reported. `--force` opts in to replacing modified managed templates. Locally customized agent content can be replaced by that explicit force operation; active model assignments are then restored from `.dado/config.yaml`. If the manifest is missing, uninstall refuses to guess which files belong to DADO and asks for manual inspection.

Global executable installation is separate from project initialization. From source, `python -m pip install .` (or use `scripts/install.sh` / `scripts/install.ps1`). Update from source with `python -m pip install --upgrade .`, then run `dado update` inside the project. Remove the CLI with `pipx uninstall dado-orchestration` or `python -m pip uninstall dado-orchestration`. `dado uninstall` removes only unchanged managed OpenCode files. It preserves `.dado/work` by default; `--remove-data` requires typing `DELETE WORK`.

## Permissions and limitation

The role files use V2 action/resource/effect rules. Provider/model permission details can vary by OpenCode release. Review the installed frontmatter and effective project/global config with OpenCode's own tools. Agent permission rules do not enforce file scope at the operating-system level. The worker must report changed files; DADO rejects result packets that claim changes outside the declared scope. No plugin tools are installed: DADO's CLI is the deterministic tool boundary, invoked through native OpenCode shell access, avoiding an extra TypeScript plugin runtime that would duplicate state logic and currently has a different V2 plugin API.
